# Motamken Backend

Laravel 13 API · PHP 8.4 · PostgreSQL 16 · Redis 7 — all running in Docker.

How the whole platform fits together: [docs/ARCHITECTURE.md](docs/ARCHITECTURE.md). Production runs on a VPS: [deploy/README.md](deploy/README.md).

## Auth API

Built to match the frontend's `authService` (motamaken-front). Set the frontend's
`NEXT_PUBLIC_API_URL` to `http://localhost:8000/api`. Errors always come back as `{ "message": ... }`
(plus `errors` for validation), in the language of the `Accept-Language` header (`ar` / `en`).

| Endpoint | Body | Response |
|---|---|---|
| `POST /auth/signup` | `method, firstName?, lastName?, username, email\|phone, password, subscribe` | `{ target }`, sends a signup OTP |
| `POST /auth/login` | `method, identifier, password` | `{ otpRequired: true }` or `{ otpRequired: false, accessToken, user }` |
| `POST /auth/otp/verify` | `purpose (signup\|login\|reset), method, target, code` | signup `{ verified }` · login `{ accessToken, user }` · reset `{ token }` |
| `POST /auth/otp/resend` | `purpose, method, target` | `{ sent: true }` (60 s cooldown) |
| `POST /auth/password/forgot` | `method, target` | `{ sent: true }`, sends a reset OTP |
| `POST /auth/password/reset` | `token, password` | `{ success: true }`, logs out all devices |
| `GET /auth/me` · `POST /auth/logout` | `Authorization: Bearer <token>` | user · `{ success: true }` |

Rules:
- **OTP**: 4 digits, valid 10 min, 5 wrong tries locks it, stored hashed in Redis. Email goes out by mail, phone by WhatsApp
  (`App\Contracts\WhatsAppSender`; the dev binding only logs, so bind a real provider in `AppServiceProvider`).
- **Login OTP**: a verified account logs in with its password alone. A code is required when the identifier isn't
  verified yet, when two-factor authentication is on, or for methods listed in `LOGIN_OTP_METHODS` (empty by default,
  e.g. `email,phone` to always ask).
- **Forgot password never returns a token directly.** The frontend then sends email users through `/forgot-password/verify` too,
  and the reset token is issued only after the code is verified.
- **Welcome points**: 50, granted the first time an account verifies an email or phone.
- **Rate limits**: 30 requests/min per IP, and 6/min per endpoint and identifier.

## Homepage & Messages API

Built from the Figma page "home page – message". Full request/response examples are in Swagger (`/swagger`),
grouped as Authentication · Homepage · Header & account · Messages.

**Sample data:** `php artisan db:seed` loads countries, cities and categories, plus (outside production) demo people,
ads and chats. Log in as **demo@motamakin.com / Secret#123** (email logins ask for a code: it arrives in Mailpit at
http://localhost:8025). `php artisan migrate:fresh --seed` rebuilds everything.

| Area | Endpoints |
|---|---|
| Homepage (public) | `GET /home` · `GET /projects` · `GET /projects/{id}` · `GET /search` |
| Dropdowns (public) | `GET /categories` · `GET /countries` · `GET /countries/{id}/cities` · `GET /currencies` · `GET /languages` |
| Header (token) | `GET /me/summary` (balance, points, unread badges) · `PATCH /me/preferences` (language, currency, theme) |
| Bell (token) | `GET /notifications` · `POST /notifications/{id}/read` · `POST /notifications/read-all` |
| Messages (token) | `GET/POST /conversations` · `GET /conversations/{id}` · `POST /conversations/{id}/read` · `GET/POST /conversations/{id}/messages` |

How it behaves:
- **Homepage**: `/home` returns the 6 featured profiles, 6 distinctive projects, the category and platform tabs, and the first tab of each list
  (cached 60 s). Other tabs: `GET /projects?category=<slug>` or `?type=influencer_request&category=instagram`.
- **Names follow `Accept-Language`** (`en`, `ar`, `fr`) for countries, cities, categories, currencies and notification texts.
- **Messages**: one conversation per pair of users. `sort` = `newest` | `oldest` | `unread`; `q` searches the other person's name.
  Text goes as JSON; voice messages and attachments as `multipart/form-data` (`file`, plus `duration` in seconds for voice).
  Allowed files: images, pdf, office documents, txt/csv, zip/rar, up to 20 MB. They are stored privately and served through
  signed links that expire after an hour.
- **Read receipts**: `POST /conversations/{id}/read` when the chat is opened clears the badge and turns the sender's `sent` into `read`.
- **No realtime yet**: poll `GET /conversations/{id}/messages?after=<last id>` every few seconds. Online status comes from
  activity in the last 2 minutes.

## Projects & proposals API

Post a project, send offers, accept or decline them. Swagger group: **Projects & proposals**.

| Who | Endpoints |
|---|---|
| Owner | `POST /projects` · `PATCH /projects/{id}` · `DELETE /projects/{id}` · `POST /projects/{id}/close` · `POST /projects/{id}/complete` · `GET /me/projects` |
| Owner (offers) | `GET /projects/{id}/proposals` · `POST /proposals/{id}/accept` · `POST /proposals/{id}/decline` |
| Freelancer / influencer | `POST /projects/{id}/proposals` · `PATCH /proposals/{id}` · `POST /proposals/{id}/withdraw` · `GET /me/proposals` |
| Either side | `GET /proposals/{id}` |
| Profile | `GET /me/profile` · `PUT /me/profile` ("Add Your Profile") |

Rules:
- **Project life cycle**: `open` (public) → `in_progress` (an offer was accepted) → `completed`; or `open` → `closed` (cancelled).
  Only open projects are public; the owner and people who sent an offer can still open the others.
- **Kinds**: `project` ads are for freelancer profiles and take project categories; `influencer_request` ads are for influencer
  profiles and take a platform category (Instagram, ...). The kind cannot change after posting.
- **Offers**: one per person per project, editable or withdrawable while `pending`. Needs a profile of the right kind and a project
  that is open and not your own. Accepting one offer declines the other pending ones; closing a project declines them all.
  Everyone involved gets a bell notification (`proposal.received`, `proposal.accepted`, `proposal.declined`).
- **Refusals carry a `code`** next to the message, so the frontend can react: `profile_required` (send the user to
  "Add Your Profile"), `profile_type_mismatch`, `own_project`, `already_offered`, `project_not_open`, `proposal_not_pending`,
  `project_has_proposals`, `project_not_editable`, `project_not_in_progress`.
- Sample offers for the demo account load with `php artisan db:seed` (or `--class=DemoProposalsSeeder` on an existing database).

## Payment methods & quick feedback API

| Endpoint | Body | Response |
|---|---|---|
| `GET /me/payment-methods` | — | saved cards / PayPal accounts, preferred first |
| `POST /me/payment-methods` | card: `type=card, holderName, number, expMonth, expYear, cvc, makeDefault?` · PayPal: `type=paypal, email, makeDefault?` | the saved method (201) |
| `POST /me/payment-methods/{id}/default` | — | the method, now preferred |
| `DELETE /me/payment-methods/{id}` | — | `{ success: true }`; the newest remaining method becomes preferred |
| `POST /feedback` | `context (deposit\|withdrawal\|promotion\|subscription\|payment_method\|escrow), referenceId?, rating (up\|down), comment?` | `{ success: true }` (201) |

Rules:
- **Card numbers are never stored.** The number (Luhn-checked), expiry (not in the past) and CVC go to
  `PaymentGateway::saveCard()`, which returns the provider's token; only the brand, last 4 digits, expiry and holder
  name are kept. The token and PayPal email are encrypted at rest. A real gateway should tokenize in the browser
  (e.g. Stripe Elements) and send the token instead of the card number.
- The first saved method is always the preferred one.

## Escrow: split approval & tips

| Endpoint | Body | Response |
|---|---|---|
| `POST /projects/{id}/escrow/split/approve` | — | the escrow; the member's `splitStatus` is `approved` |
| `POST /projects/{id}/escrow/split/object` | `note` (5–1000 chars) | the escrow; `objected`, client and team notified |
| `POST /projects/{id}/escrow/tip` | `amount, note?` | the escrow with `tips` |

Rules:
- Team escrows start with every member's split `pending`; solo escrows are `approved`. While `splitApproved` is false,
  `POST /milestones/{id}/approve` answers `split_not_approved`. Admin dispute settlements are not blocked.
- Tips need at least one released milestone (`tip_too_early`), come from the client's wallet (`insufficient_funds`),
  are split by share like payments, and carry no platform fee (ledger type `tip`).

## Settings API: account, notifications, two-factor, devices

| Endpoint | Body | Response |
|---|---|---|
| `PATCH /me` | `firstName?, lastName?, username?, subscribed?` | the user (email / phone are not changed here) |
| `POST /me/password` | `currentPassword, password, password_confirmation` | `{ success }`; every other token is deleted |
| `GET /me/notification-settings` · `PATCH` | `{ messages?, proposals?, projects?, payments?, disputes? }` | `{ data: {group: bool}, required: ["account"] }` |
| `GET /me/security` | — | `{ twoFactor: {enabled, method, target}, passwordChangedAt, sessions: [{id, device, ip, lastUsedAt, isCurrent}] }` |
| `POST /me/two-factor` | `method (email\|phone), password, target` | `{ sent, target }` (masked); a code is sent to `target` |
| `POST /me/two-factor/resend` · `/confirm` (`code`) · `/disable` (`password`) | | the security object |
| `DELETE /me/sessions/{id}` · `POST /me/sessions/logout-others` | — | `{ success, wasCurrent }` · `{ success, count }` |

Rules:
- **Two-factor login**: when it is on, `POST /auth/login` always answers `{ otpRequired: true, twoFactor: {method, target} }` and
  sends the login code to the second factor, whatever the login method. `/auth/otp/verify` and `/auth/otp/resend` with
  `purpose=login` keep using the login identifier; the backend checks the code against the second factor.
- **Email notifications**: bell notifications belong to groups (`config/notifications.php`). After one is stored, the
  `EmailActivityNotification` listener (auto-discovered, do not register it again) queues an `ActivityEmail` when the
  user wants that group by email. Restart the `queue` container after changing notification code.
- **Devices**: every token records the IP and user agent when it is created (`IssuesTokens::newToken`).

## Deploy on Render

An alternative to the VPS setup in [deploy/README.md](deploy/README.md), which is what production uses.

Everything is described in [`render.yaml`](render.yaml) (a Render Blueprint) and built from [`Dockerfile.render`](Dockerfile.render)
(FrankenPHP, PHP 8.4, production settings in `docker/render/`). Local development keeps using `Dockerfile` + `docker-compose.yml`.

| Render resource | What it runs |
|---|---|
| `motamakin-db` (Postgres 16) | the database (`DB_URL`) |
| `motamakin-redis` (Key Value) | cache, sessions, queues, OTP codes (`REDIS_URL`) |
| `motamakin-api` (web) | the API on `$PORT`; runs `migrate --force` on start (`RUN_MIGRATIONS=true`); health check `/up`; uploads on a 5 GB persistent disk at `storage/app` |
| `motamakin-queue` (worker) | `queue:work` (emails, notifications) |
| `motamakin-scheduler` (cron, every minute) | `schedule:run` (team invitations, subscription renewals, prize draws) |

Steps:

1. Push this repository to GitHub, then in Render: **New → Blueprint** → choose the repository.
2. Fill the values Render asks for (`sync: false`):
   - `APP_KEY`: run `php artisan key:generate --show` locally and paste the `base64:...` value.
   - `FRONTEND_URL` and `CORS_ALLOWED_ORIGINS`: the frontend address, e.g. `https://motamaken-front.vercel.app`.
   - `MAIL_HOST`, `MAIL_USERNAME`, `MAIL_PASSWORD`: an SMTP provider (Brevo, Mailgun, SES...). OTP codes are sent by email.
3. Apply. The first deploy creates the tables. To add the reference data (countries, cities, categories, plans), open the
   `motamakin-api` **Shell** and run `php artisan db:seed --class=ReferenceDataSeeder --force`
   (`php artisan db:seed --force` also adds the demo people and projects, unless `APP_ENV=production`).
4. Point the frontend at the API: `NEXT_PUBLIC_API_URL` and `API_URL` = `https://<motamakin-api>.onrender.com/api`.
   Keep `NEXT_PUBLIC_PAYMENTS_SIMULATE=true` while `APP_ENV=staging` and the fake gateway are used.

Good to know:
- `APP_URL` defaults to Render's `RENDER_EXTERNAL_URL`; set it only for a custom domain. Proxies are trusted, so links are `https`.
- Uploads (avatars, portfolio, identity documents, chat and dispute files) are on the web service's disk, so it runs
  one instance. To scale out, move the `public` and `local` disks to S3-compatible storage (install
  `league/flysystem-aws-s3-v3` and switch the disks' drivers).
- The image caches config, routes, views and events at start; change environment variables in Render, not in code.
- Before real money: bind a real `PaymentGateway`, set `APP_ENV=production` (this disables `/wallet/deposits/{id}/simulate`),
  and set `NEXT_PUBLIC_PAYMENTS_SIMULATE=false` on the frontend. WhatsApp OTP sending still uses `LogWhatsAppSender`.

## Promotion campaigns API

Pay-per-visit promotion (the "Promo" screens). Swagger group: **Promotion campaigns**.

| Who | Endpoints |
|---|---|
| Advertiser | `POST /campaigns` · `PATCH /campaigns/{id}` · `POST /campaigns/{id}/launch` · `/pause` · `/resume` · `/cancel` · `GET /me/campaigns` |
| Advertiser (reports) | `GET /campaigns/{id}` (stats, rejection pie, top promoters) · `GET /campaigns/{id}/visits` (filtering screen) · `/promoters` · `/daily` |
| Promoter | `GET /campaigns/available` · `POST /campaigns/{id}/join` (get the link) · `GET /me/promoter` (dashboard) |
| Website | `POST /campaign-visits` `{code}`: called by the `/r/{code}` page from the visitor's browser; answers the `path` to show |
| Admin | `GET /admin/campaigns` · `POST /admin/campaigns/{id}/cancel` · `GET /admin/affiliate` (affiliate monitoring) |

How it works:
- A campaign is a draft until launched; launching takes the whole budget from the wallet into the campaigns account.
- Each **valid** visit costs the advertiser `costPerVisit`: the promoter gets it minus the platform fee (`fee_percent`, 20%).
- Links only lead to the owner's own project or profile on the website, never to an outside address.
- **Filtering**: visits are always recorded, but not paid when they come from a robot (`bot`), a repeat visitor within
  `unique_window_hours` (`duplicate`), a promoter over `max_visits_per_promoter_per_hour` (`rate_limited`), a country
  outside `allowed_countries` (`country`, needs a CDN sending `CF-IPCountry`), the promoter or owner themselves (`own_link`),
  or while the campaign is paused or out of money.
- When the budget can't cover another visit, or the end date passes (`campaigns:close-ended`, every 15 minutes), the
  campaign completes and what is left goes back to the owner. Stopping it early refunds the same way.
- **Frontend**: needs a page at `/r/{code}` that POSTs the code (and `document.referrer`) to `/campaign-visits`, then
  navigates to the returned `path`.

## The website's proxy and the visitor's IP

The website calls the API from its own server, so without help every visitor looks like that server: rate limits would
be shared by everyone and campaign/affiliate visits would all count as one person. The website therefore sends the
visitor's IP, browser and country in `X-Client-*` headers, signed with a shared secret:

- backend `.env`: `FRONTEND_PROXY_SECRET=<long random string>`
- website server env: `API_PROXY_SECRET=<the same string>` (server-only, never `NEXT_PUBLIC_`)

Without the matching secret the headers are ignored, so they cannot be forged by calling the API directly. If the
secret is missing, campaign visits made through the website are rejected as robots (the server's `node` user agent),
which makes the misconfiguration easy to spot.

## Card payments (Moyasar)

`PAYMENTS_DRIVER=moyasar` charges real cards through [Moyasar](https://moyasar.com); `fake` (the default, and what the
tests use) keeps the development flow with `POST /wallet/deposits/{id}/simulate`.

- **Keys:** `MOYASAR_SECRET_KEY` (sk_…) here, server only. The publishable key (pk_…) goes to the website as
  `NEXT_PUBLIC_MOYASAR_PUBLISHABLE_KEY`. Test keys (`sk_test_` / `pk_test_`) never charge anyone; swap both for the live
  keys to go live.
- **How a payment works:** the browser sends the card straight to Moyasar and gets a token; card numbers never reach
  this API. `POST /wallet/deposits` with `cardToken` (or `paymentMethodId` for a saved card) charges it; the deposit's
  UUID is Moyasar's payment id, so a retry never charges twice. 3-D Secure runs on Moyasar's page, which returns to
  `FRONTEND_URL/payments/return?deposit={id}`; the site then calls `POST /wallet/deposits/{id}/refresh`, which re-reads
  the payment from Moyasar and credits the wallet only when it is `paid` for exactly the right amount and currency.
- **Saved cards:** the customer confirms the card once with their bank; `POST /me/payment-methods` with `token` accepts
  only tokens Moyasar reports as `active` and reads brand / last 4 / expiry from Moyasar. Later payments usually need
  no bank page.
- **Webhook (recommended):** in the Moyasar dashboard add `https://<api>/api/webhooks/moyasar` for payment events with
  `MOYASAR_WEBHOOK_SECRET` as the secret token. It settles payments whose customer closed the tab before returning.
- Paying for something by card (promotions, subscriptions) tops the wallet up with exactly the price
  (`purpose: purchase`, which waives the top-up minimum) and then pays from the wallet, so every purchase stays in the
  ledger. Withdrawals are still paid out by an admin.
- Test card: `4111 1111 1111 1111`, any future expiry, any CVC; Moyasar's test bank page lets you approve or decline.

## Admin panel: staff, audit, moderation and settings

- **Staff roles**: `admin_roles` with permissions from `config/admin.php`; routes use `admin.can:<permission>`. An admin
  without a role has full access. Every non-GET admin call is written to `admin_logs` (`GET /admin/audit`).
- **Policies**: Site settings (`/admin/site-settings`) hold the site identity and links, maintenance mode (API answers
  503 `maintenance` to everyone but the staff), upload limits, offered payment methods and "staff must use two-factor".
  Values that replace config (promotion prices, point rules, payment methods, SMTP) are applied by
  `App\Support\RuntimeConfig` at boot and before every queued job.
- **Moderation**: blacklist (emails, phones, domains, IPs, words), report priorities and actions, hidden projects and
  reviews, dispute appeals with ledger corrections, support tickets, contact replies, notification texts, announcements.
- **Exports**: `GET /admin/export/{dataset}` streams CSV (UTF-8 with BOM, opens in Excel).

### AI (optional)

Off by default. Set `AI_ENABLED=true` and `OLLAMA_URL` (self-hosted Ollama with `llama3.2:3b` and
`nomic-embed-text`). New content is screened in a queued job (`App\Jobs\ScreenContent`); suspicious items become reports
with source `ai`. Matching needs pgvector: the Postgres image in `deploy/postgres` includes it; after it runs, migrate and
`php artisan ai:embed` to fill the embeddings.
